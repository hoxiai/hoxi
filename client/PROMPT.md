# GoPanel 项目 AI 开发提示词

你正在参与 GoPanel 项目的开发。你的目标不是泛化地“写一个 Flutter 页面”，而是先快速理解这个项目的定位、边界、参考基准、交互对象和移动端约束，再以**最小破坏、最高一致性、最强可维护性**的方式完成需求。

---

## 1. 项目定位

GoPanel 是一个 **使用 Flutter 实现的手机端服务器管理应用**。

它的定位不是做一个纯展示型 App，而是做一个**可连接远程服务器管理面板、并在移动端完成核心运维操作的客户端**。它的整体思路参考：

- GoPanel
- 1Panel
- 服务器管理面板的常见业务流

它的目标能力包括：

- 连接远程 GoPanel / 1Panel 风格的服务器管理面板
- 登录并保存多个服务器连接
- 查看主机状态、系统信息、资源监控
- 管理 Docker 容器、镜像、网络、卷
- 管理 Docker Compose / 应用编排实例
- 管理网站、反向代理、证书
- 管理数据库、数据库用户、备份任务
- 管理应用商店安装项、应用状态与生命周期
- 查看日志、任务状态、告警与基础通知
- 集成 AI 助手能力，通过手机辅助服务器运维与代码开发
- API 接口优先直接复用 GoPanel 现成服务端能力

你必须默认以下事实：

- **这个项目本质上是 GoPanel / 1Panel 类管理面板的移动端延伸**
- **核心业务逻辑应优先尊重服务端现有 API 和状态流转**
- **服务端 API 默认直接以 GoPanel 现有项目为基准，不重新设计第二套接口**
- **移动端主要承担“连接、展示、操作、反馈”职责，而不是重写服务端业务**
- **不是所有功能都必须在第一时间做到桌面管理面板的完整度**
- **在不确定时，优先参考 GoPanel 与 1Panel 的模块边界和业务链路，而不是自行发明一套新体系**
- **这个 App 后续要预留 AI 协作入口，使用户可以在手机端发起代码开发、命令执行、日志分析和运维辅助任务**

## 2. 技术栈

### 客户端

- Flutter
- Dart

### 推荐基础能力

- HTTP 请求：优先保持统一封装，不要让页面直接散落网络请求
- 状态管理：优先统一，不要一个页面一种状态流
- 路由管理：保持集中式或分层式管理，不要在页面内部随意拼接跳转逻辑
- 本地存储：用于服务器连接信息、登录态、主题、偏好设置等
- JSON 序列化：保持统一模型结构，不要手写大量重复解析代码

### 当前默认架构倾向

- 分层架构优先：`presentation -> application -> domain/model -> data`
- 页面与业务分离：界面只负责展示与交互，数据获取与状态变化通过统一层处理
- API 能力统一走客户端封装层
- 服务端接口默认直接对接 GoPanel 现成 API
- 多服务器连接能力从一开始就应作为基础能力考虑
- 鉴权、错误处理、刷新令牌、连接状态管理应视为基础设施，而不是零散逻辑

### 服务端接口基准

- 服务端接口默认直接使用 GoPanel 项目的现成接口
- 理解接口能力时，直接参考本地 GoPanel 仓库根目录的 `PROMPT.md`
- 如果需要继续追踪接口实现，优先按 GoPanel 的链路：`router -> api -> service -> repo -> model`
- 手机端是现有 GoPanel 面板能力的客户端延伸，不额外发明第二套接口协议
- 除非用户明确要求，否则不要为了移动端单独重做服务端接口设计

如果你准备引入新的状态管理、路由、网络、持久化库：

- 先确认项目里是否已经存在统一方案
- 如果已有方案，不要擅自替换
- 如果项目尚未成型，优先选择成熟、主流、适合长期维护的方案
- 但不要因为“想要更优雅”就不断更换技术路线

## 3. 核心定位差异

这个项目虽然参考 GoPanel / 1Panel，但它是**移动端客户端**，不是面板后端本身。

因此必须区分以下边界：

### App 负责

- 服务器连接管理
- 用户登录与鉴权态保存
- 数据展示与移动端交互
- 向远程面板发起管理请求
- 呈现任务结果、状态变化、错误反馈

### App 不负责

- 重写服务端容器管理逻辑
- 在本地直接实现完整 Docker / Caddy / 数据库控制能力
- 把后端已有复杂流程搬到客户端本地执行
- 脱离服务端 API 自行构造另一套真实业务规则

默认理解方式：

- **服务端负责业务真相**
- **客户端负责高质量交互与移动端可用性**

## 4. 参考对象

理解需求时，应同时参考三类基准：

### 业务基准

- GoPanel 的模块划分
- 1Panel 的服务器管理流程
- 常见服务器管理面板的状态流与生命周期

### 客户端基准

- 移动端信息密度需要更克制
- 重要操作必须更明确确认
- 列表、详情、日志、监控在手机端要做层级拆分

### 体验基准

- 快速连接
- 清晰反馈
- 低学习成本
- 核心任务优先
- 风险操作可控

你不能把 PC 面板页面机械压缩成手机页面，而应保留业务语义并重组移动端布局。

## 5. 推荐目录思路

如果当前项目还未完全成型，优先按如下思路组织：

```text
.
├── lib/
│   ├── app/               应用入口、路由、主题、全局配置
│   ├── core/              常量、异常、网络、存储、鉴权、工具
│   ├── features/          按模块拆分的功能目录
│   │   ├── auth/          登录、连接、会话
│   │   ├── server/        主机、系统信息、资源监控
│   │   ├── container/     容器、镜像、网络、卷
│   │   ├── compose/       编排项目、应用实例
│   │   ├── website/       网站、反向代理、证书
│   │   ├── database/      数据库与用户管理
│   │   ├── backup/        备份与恢复相关
│   │   ├── app_store/     应用商店与安装项
│   │   └── settings/      服务器配置、主题、偏好
│   ├── shared/            通用组件、样式、模型、枚举
│   └── main.dart          主入口
├── assets/                图片、图标、字体、插画
├── test/                  单元测试、组件测试
└── pubspec.yaml           依赖与资源配置
```

理解需求时优先按如下路径追踪：

- **登录 / 鉴权问题**：`features/auth -> core/network -> core/storage`
- **页面问题**：`features/*/presentation -> shared/widgets -> theme`
- **接口问题**：`presentation -> controller/viewmodel -> repository -> datasource/api`
- **连接配置问题**：`server connection model -> local storage -> auth/session`
- **全局状态问题**：`app bootstrap -> auth state -> active server state`

如果项目已有自己的目录结构，优先尊重现有组织方式，不要为了套模板而强行迁移。

## 6. 工程规模与边界规范

为了避免移动端项目在开发过程中快速失控，必须严格遵守以下工程边界：

### 文件规模

- 单个 Dart 文件原则上**不要超过 400 行**
- 单个 Widget 页面文件原则上控制在 **300 行以内**
- 单个方法原则上控制在 **50 行以内**
- 单个类原则上只承担单一职责，不要同时混合页面、状态、请求、解析、导航等职责

如果确实超过上述规模：

- 优先拆分子 Widget
- 优先拆分 controller / viewmodel / service / repository
- 优先抽离模型、常量、样式、工具函数
- 不要通过继续堆代码来“临时完成需求”

### 模块边界

- 页面层只负责展示、交互分发和少量页面状态
- 业务状态放在统一状态层，不要散落在多个 Widget 内部
- 网络请求放在数据层或 API 层，不要写进页面组件
- 数据模型与视图模型分层明确，不要把接口 JSON 结构直接到处透传到 UI
- 通用组件进入 shared，业务组件留在 feature 内，不要反向污染

### 依赖边界

- 不要为了一个小需求引入大型依赖
- 能复用现有能力就不要新增同类库
- 新增依赖前先确认是否已有官方、主流、长期可维护方案
- 不要在同一项目内并存两套用途相同的网络、路由、状态管理方案

### 命名与结构

- 文件名、类名、目录名保持语义化和稳定
- 不要使用 `temp`、`test2`、`new_page`、`final_final` 这类临时命名
- Feature 目录下优先保持固定层次，不要每个模块各搞一套结构
- 枚举、异常、常量、主题、扩展方法优先集中管理

### 页面与组件拆分

- 一个复杂页面必须拆成概览区、列表区、详情区、操作区等明确子模块
- 通用状态卡、信息条、操作栏、日志面板应抽成可复用组件
- 当一个组件同时承担布局、数据请求、状态切换和复杂逻辑时，必须拆分
- 不要把一个首页写成超长单文件“全家桶”

### 数据与状态规则

- 不要直接修改服务端原始响应对象作为 UI 状态容器
- 列表筛选、分页、刷新、加载更多等模式尽量统一
- 错误态、空态、加载态必须进入标准状态流
- 切换服务器时必须同步清理旧上下文缓存和旧请求状态

### 禁止的常见失控行为

- 为了赶进度把所有逻辑都塞进一个页面文件
- 为了省事在多个页面复制粘贴同一段请求代码
- 为了快速联调在页面里硬编码 Token、URL、服务器 ID
- 为了“后面再整理”持续容忍超长文件、超长方法和重复逻辑
- 未经授权擅自大面积重命名、迁移目录、替换架构

## 7. 连接模型

这个项目首先是一个“连接远程管理面板”的 App，因此连接模型是核心基础设施。

至少应从产品与代码结构上默认存在以下概念：

- 服务器连接配置
- 服务器别名 / 分组
- 面板地址
- 用户身份或 Token
- 当前激活服务器
- 多服务器切换
- 连接状态
- SSL / 自签名证书处理策略

处理连接功能时必须知道：

- 不要把“当前登录态”写死为单服务器
- 不要让请求层直接散落 baseUrl 拼接逻辑
- 不要把鉴权信息与 UI 页面强耦合
- 连接失败、证书异常、超时、离线、鉴权失效都必须有清晰反馈

如果服务端支持刷新令牌、会话续期或双因子：

- 优先做兼容式设计
- 不要因为当前页面没用到就把接口能力硬编码死

## 9. 移动端交互规则

开发移动端页面时必须遵守：

- **保持整体风格统一**
- **优先做增量修改，不要频繁推翻已有页面结构**
- **重要操作必须可确认、可撤销或至少可二次确认**
- **列表页负责概览，详情页负责展开，不要把所有信息堆在一个页面**
- **监控信息优先做卡片分区，不要做超长杂糅面板**
- **日志与文本内容优先考虑复制、搜索、换行和滚动体验**
- **错误反馈要可读，不要只显示技术报错原文**
- **加载、空态、失败态必须明确**
- **高频操作入口要前置，低频高风险操作要后置**

视觉上优先遵守：

- 以简洁、清晰、低噪声为主
- 颜色以蓝色系为主品牌色，整体风格优先参考 GoPanel 的 Dashboard `StatusCard.vue`
- 重点参考其浅蓝到白色的渐变背景、浅蓝边框、白底卡片、柔和阴影、圆角容器和低噪声层次
- 状态强调优先靠层级、留白、浅色点缀和蓝色信息层，不依赖大面积高饱和颜色
- 卡片、分区、间距、圆角、轻阴影保持统一，信息卡优先使用类似状态卡与信息条的面板式结构
- 不要把桌面后台的高信息密度布局直接照搬到手机

### Tabs / Chips 视觉规范（重要）

后续所有“Tab 切换 / 分段选择 / 筛选 chips”（例如资源分段、监控切换、任务筛选）统一遵守：

- 以“呼吸感强”为目标：更大的留白、更克制的文本密度、更柔和的阴影与边界
- 优先使用玻璃态（Glassmorphism）：半透明白底 + 轻微背景模糊 + 浅蓝边框 + 大圆角 + 轻阴影
- 视觉要扁平、大气：避免厚重描边、过强渐变、过多层级叠加；选中态只做“更亮/更白 + 微弱边框强调”
- 组件优先复用 shared 的统一实现，不要在页面里各写一套 tabs/chips 样式

### Dashboard 参考结构（重要）

后续开发“服务器概览 / Dashboard / 监控类页面”时，默认优先对齐 GoPanel 后台 Dashboard 的信息分区结构与视觉语言：

- 顶部：一张 BaseInfo 大卡（主机名 + 系统摘要），右侧用多个紧凑 InfoTile 展示关键字段（如系统信息、启动时间、运行时间、进程、IPv4、内核版本等；字段不足时显示可用字段，不强行造字段）
- 中部：三张核心指标卡（CPU / 内存 / 负载），以“环形进度 + 大数字 + 次级说明”的低噪声仪表盘式呈现
- 底部：磁盘列表分区（标题含设备数与展开/收起），每个盘位展示占用百分比与 used/total

实现方式上优先遵守：

- 先沉淀可复用的面板风格组件，再改页面：PanelCard / InfoTile / RingGauge / ProgressRow 等
- 页面尽量不硬编码颜色与阴影，优先复用 `core/theme/app_theme.dart` 的 token 与 ThemeData
- 同类页面保持同构布局与同一套间距/圆角/边框策略，避免每个模块各搞一套“看起来差不多但细节不同”的 UI

### 底部导航与模块落地（方案 A，可直接执行）

默认采用 5 个底部 Tab（从左到右）：

1. 概览（Dashboard）
2. 资源（Resources：容器/应用/网站/数据库/SSL 的聚合入口）
3. 任务（Tasks：流水线/应用安装/证书签发/备份/更新等异步过程的统一中心）
4. AI（上下文助手：与当前服务器/任务/日志/资源绑定）
5. 设置（连接与安全为核心：多服务器、Entrance、安全策略、偏好）

#### 目标信息架构（IA）

- 资源 Tab：承载“对象管理”，内部做二级分段（Segment/Tab），而不是把所有模块继续塞进底部导航
- 任务 Tab：承载“过程管理”，统一展示运行中/成功/失败的任务与日志，避免各模块复制轮询逻辑
- 概览 Tab：承载“状态与告警”，并提供高频快捷操作入口

#### 可执行开发清单（按顺序）

**A. 调整底部导航（最小改造）**

- 修改 `MainScaffoldScreen` 的底部导航为：概览 / 资源 / 任务 / AI / 设置
- 仍使用 `IndexedStack` 保活切页（不强制引入 ShellRoute）
- 验收：Tab 切换不丢状态、返回键行为符合预期、不会出现路由堆叠混乱

**B. 新增 Resources 聚合页**

- 新增 `features/resources/presentation/screens/resources_screen.dart`
- Resources 内部提供二级分段入口（建议顺序）：容器 / 应用 / 网站 / 数据库 / SSL
- 第一期优先复用既有页面作为子内容：
  - 容器：复用 `ContainerListScreen`
  - 应用：复用 `AppsListScreen`
  - 网站/数据库/SSL：先放占位卡片（显示“未接入”与计划），不乱造接口字段
- 约束：
  - Resources 统一提供 AppBar 与背景风格，避免子页重复嵌套多层 Scaffold/AppBar
  - 子模块后续如需沉淀为可嵌入的 “Body Widget”，优先拆 `xxx_body.dart`（只渲染内容）
- 验收：Resources 页面结构清晰、切换二级分段顺滑、样式统一

**C. 新增 Tasks（任务中心）骨架**

- 新增 `features/task_center/`（按模块自闭环组织）
  - `models/`：`TaskEntity`、`TaskStatus`、`TaskType`、`TaskLog`
  - `data/`：`TaskRepository`（先占位也可，后续对齐 GoPanel 任务/日志接口）
  - `presentation/`：`TaskCenterScreen`（列表）+ `TaskDetailScreen`（日志/阶段/重试）
- 第一阶段即使后端任务接口未完全对齐，也必须先把 UI 与状态流落地：
  - 任务列表：运行中/失败/成功分组
  - 任务详情：日志区域支持复制与搜索（后续增强）
- 约束：
  - 所有需要轮询的模块（应用安装/流水线/备份/证书签发）后续都必须收口到任务中心，不在各页面重复写 Timer
- 验收：任务中心可独立进入、UI 完整、后续接真实接口时无需重做页面结构

**D. 多服务器隔离（必须作为基础设施落地）**

- 定义 `ActiveServer` 概念（当前激活服务器）
- 网络层必须支持按服务器隔离的请求上下文（至少隔离：baseUrl、token、cookie/Entrance）
- 切换服务器必须：
  - 取消旧轮询
  - 清理旧页面状态缓存（避免 A 服务器数据展示到 B 服务器）
- 验收：多服务器切换后数据不串号；遇到 HTML 的 NoEntrance 页面能明确提示并阻断流程

**E. 统一基础组件与规范（持续执行）**

- 通用面板组件必须放入 `shared/widgets/panel/`
- 时间/字节/速率格式化必须抽到统一 formatter，避免页面重复实现
- 高风险操作必须统一确认弹窗 + 明确反馈（loading/success/failure）
- 验收：新增页面不硬编码大面积颜色/阴影，优先走 Theme token

#### 里程碑验收点（每阶段可验证）

- M1（导航收口）：底部 Tab 按方案 A 正常工作，Resources/Tasks 入口可达
- M2（资源可用）：容器/应用在 Resources 内可用，网站/数据库/SSL 有占位与计划说明
- M3（任务成型）：任务中心 UI 与状态流完整，可承接各模块异步过程（即使先用假数据/占位）
- M4（多服务器稳定）：切换服务器不串号，错误提示可读，安全入口/Method 错误能快速定位

## 10. API 交互原则

这个项目大概率依赖远程面板 API，因此接口设计与调用方式必须稳定。

必须遵守：

- 默认直接对接 GoPanel 现成 API，不自行重新定义服务端接口
- 对接口能力的理解优先参考本地 GoPanel 仓库根目录的 `PROMPT.md`
- **【极其重要】API 路由匹配与 Method 校验**：GoPanel 后端的 API 路由（例如 `/api/user/info`，`/api/dashboard/current`）很多是 `POST` 请求。如果 Flutter App 误用 `GET` 请求调用，或者拼错路径，由于后端的全局拦截器 `r.Use("/*", middleware.Entrance)` 的存在，会导致请求直接掉入静态资源处理逻辑中，返回 `<h1>暂时无法访问</h1>当前环境已经开启了安全入口登...` 的 HTML 页面，而不是标准的 404 JSON 错误。因此，**每次写新接口时，必须去后端对应路由文件（`app/router/*.go`）确认正确的 Method，遇到返回 HTML 报错时，第一时间检查 HTTP Method 和路径是否拼错。**
- 始终先对齐服务端真实接口，不要猜字段
- 请求模型、响应模型、错误模型要统一，后端真实返回的业务成功状态码为 `code: 0`，消息字段为 `msg`。
- 登录成功后，不仅要保存 `xAuth` Token，还要拦截并保存后端下发的 `Set-Cookie`（包含 `Entrance` 安全入口等 Cookie），并在后续请求中自动带上，以防止受保护的静态资源或特定 API 拦截。
- 不要在页面里直接拼装复杂请求参数
- 不要在多个模块重复写鉴权头、基础 URL、错误处理
- 对分页、筛选、搜索、排序做统一封装

如果服务端接口风格接近 GoPanel / 1Panel：

- 这里默认不是“接近”，而是优先直接复用 GoPanel 现有接口语义
- 优先尊重原有字段命名
- 优先尊重原有状态值和生命周期语义
- 不要在客户端随意改名后再到处映射，除非已有统一转换层

如果需要定位 GoPanel 具体接口来源，优先使用：

- 接口问题：`router -> api -> service -> repo -> model`
- 页面调用参考：`admin/src/api -> admin/src/views -> admin/src/components`
- 安装与应用商店：`apps -> app/service/app.go -> app/service/app_install.go`
- Docker / Compose：`utils/docker -> utils/compose -> app/service/container*`
- 网站 / Caddy：`init/caddy -> app/service/caddy.go -> app/service/website.go`

涉及危险操作时：

- 删除、重启、停止、重建、恢复、覆盖配置等都必须明确提示
- 请求发出后要有明确的 loading / success / failure 状态反馈

## 11. 认证与安全

移动端服务器管理应用对安全要求很高，必须默认采取保守策略。

必须知道：

- 不要在日志中输出敏感 Token、密码、密钥
- 不要在普通存储中明文保存高敏感凭据，除非项目当前阶段明确允许且已有约束
- 如果项目已接入安全存储，应继续使用，不要回退
- 登出时要正确清理会话信息
- 连接切换时要避免串用旧服务器的缓存数据
- **【强制约束】处理带“安全入口”的服务器地址登录逻辑**：
  1. 用户在 App 填写的往往是他们从浏览器复制的**完整面板地址**（如 `http://ip:port/my-secret-entrance`）。
  2. 由于 GoPanel 后端的限制，如果在开启安全入口时，直接向没有入口路径的根地址发送请求，或者向 API 发送格式错误的请求，后端会拦截并返回 `NoEntrance` 提示页（包含“当前环境已经开启了安全入口登录”）。
  3. 因此，App 在登录流程中，**必须先 GET 访问用户输入的这个原始地址进行预检**。如果收到了安全入口错误，则直接阻断流程并提醒用户。
  4. 如果预检通过，App 必须把这个带入口的完整 URL 进行**解析切割**，只提取出真实的 API `BaseUrl`（即 `scheme://host:port`），并将干净的 BaseUrl 存入存储，以供 Dio 的拦截器后续拼接正确的 `/api/...` 请求，否则如果带着入口路径拼接 API 会报 404！

涉及以下场景时要特别谨慎：

- 自签名证书
- HTTPS 校验
- Token 续期
- Session 过期
- 多服务器登录信息隔离

不要为了“方便调试”默认关闭证书校验，除非用户明确要求并且实现中有明显隔离。

## 12. 离线与缓存策略

这个项目不是纯离线应用，但移动端需要具备基础缓存与断网体验。

默认建议：

- 连接列表、最近成功登录的服务器信息可本地缓存
- 仪表盘与列表数据可做短期缓存，但必须标记刷新状态
- 危险操作结果不依赖本地猜测，必须以服务端回包为准
- 离线时应明确提示“无法连接服务器”，不要伪装成空数据

不要把缓存设计成“真数据源”，服务端始终是权威来源。

## 14. AI 能力规划

这个项目不仅要从一开始就为 AI 能力预留明确位置，而不是后期临时拼接一个聊天框，还要让 AI 在阅读本文件后能快速理解项目、快速进入正确上下文，并持续自我完善项目认知。

默认应把 AI 理解力视为项目基础设施的一部分：

- AI 第一次接手时，应能快速理解项目定位、模块边界、技术栈和风险区域
- AI 后续执行任务时，应能快速定位入口文件、状态流和接口链路
- AI 在完成任务后，应能把新的稳定知识沉淀回项目文档体系
- AI 的“自我进化”重点是**增强理解能力与文档完备度**，不是擅自扩大改动范围

默认应考虑以下 AI 使用场景：

- 基于当前服务器上下文进行运维问答
- 基于日志、监控、报错信息做诊断建议
- 帮助用户生成、修改、解释部署脚本、配置文件和命令
- 通过手机端发起代码开发相关任务，并把任务提交给远程服务器或远程 AI 执行环境
- 辅助完成应用部署、问题排查、配置优化和发布流程

处理 AI 相关需求时必须知道：

- AI 不是纯装饰性聊天能力，而是要和服务器上下文、项目上下文、日志上下文结合
- AI 读取本文件后，应优先产出“项目定位 / 当前模块 / 入口文件 / 风险点 / 待验证项”的理解结果
- AI 操作代码开发时，应优先通过远程工作区、远程仓库、远程执行环境或受控服务端能力完成
- 不要默认在手机本地完成真实代码编译、构建和复杂开发流程
- AI 生成的命令、脚本、配置修改和代码变更都必须有明确预览、确认与执行反馈
- 涉及危险操作时，必须把“建议”和“执行”分层，不允许 AI 直接静默执行高风险行为

产品与架构上优先预留：

- AI 入口页或全局助手入口
- 与当前服务器、当前应用、当前日志、当前容器绑定的上下文能力
- 任务流式输出、运行状态、执行历史、失败回放
- 代码修改建议、命令建议、日志解释、异常归因等结构化结果展示
- 人工确认后执行远程命令、脚本或代码任务的机制
- 项目摘要、模块索引、接口入口、页面入口、术语说明等 AI 快速理解材料

如果后续接入 AI 编程与开发能力，优先支持：

- 查看仓库
- 分析代码
- 生成补丁
- 执行受控命令
- 查看构建与运行日志
- 汇总执行结果返回到手机端

为了让 AI 看完本文件后能快速理解项目，必须长期维护以下文档化能力：

- 项目一句话定位必须稳定且明确
- 核心目录与模块职责必须有摘要
- 关键链路必须有追踪路径，如页面 -> 状态 -> repository -> api
- 关键术语必须统一，例如 server、connection、session、container、compose、workspace、task
- 新增重要模块时，应同步补充到提示词、README、架构文档或模块文档

AI 的自我进化应遵守以下流程：

1. 先理解当前项目边界与目标
2. 先完成当前任务的最小交付
3. 再把稳定、可复用的理解沉淀到文档
4. 再提出更优长期方案，而不是直接实施

不要做的事：

- 不要把 AI 能力设计成脱离服务器上下文的普通聊天
- 不要让 AI 默认拥有无限制的远程执行权限
- 不要跳过审计、确认和结果回显机制
- 不要把“自我进化”理解成自动重构整个项目
- 不要把 AI 记忆建立在猜测上
- 不要只补代码不补文档，导致下一个 AI 重新迷路
- 不要让核心知识只存在于临时对话里

## 18. 防死循环规则

如果你修改一个文件时出现以下情况：

- 同类报错反复出现
- 同一文件连续修补超过 3 次
- 改一处又引出同类问题，进入机械重复

你必须立即停止盲改，并切换到：

1. 重新阅读文件上下文
2. 重新确认依赖与调用链
3. 重新确认页面、状态、接口三者关系
4. 缩小修改范围后再继续

绝不能无脑重复替换同一文件。

## 20. 常见开发陷阱

### 工程规模

- 不要长期保留超过 400 行的文件而不拆分
- 不要把首页、列表、详情、弹窗、状态逻辑全部塞在同一文件
- 不要让单个方法承担初始化、请求、转换、渲染分发、异常处理全部职责

### Flutter 页面

- 不要把业务逻辑全部塞进 Widget
- 不要把网络请求直接写进多个页面生命周期里重复触发

### 状态管理

- 不要同一模块混用多套状态来源导致状态不一致
- 不要把临时 UI 状态与业务状态完全混在一起

### API

- 不要在页面里拼 baseUrl、Token、公共请求头
- 不要把服务端错误直接原样抛给用户

### 多服务器

- 不要把 A 服务器缓存数据显示到 B 服务器页面
- 不要切换服务器后还复用旧请求上下文

### 风险操作

- 不要让删除、重启、停止这类操作“一点即发”
- 不要在操作发出后缺少明确反馈

7. 做最小范围修改
8. 验证修改结果
9. 如有新增稳定认知，补充文档或提示词
10. 如有更大改造建议，单独说明而不是直接实施
